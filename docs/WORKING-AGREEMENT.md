# 工作协定（WORKING AGREEMENT）

三方分工与交接规则。**动手前读完，一次读完再动代码。**

| 角色 | 谁 | 职责 |
|---|---|---|
| **实现** | Claude Code（写作强、能长跑） | 自行拆分任务节点（写进 `docs/WORKPLAN.md`）· 写 `packages/*/lib` 与测试，自测通过才交 |
| **契约守门** | DeepSeek / DSH 会话 | 定接口、定不变量、评审、跑宿主内探针 |
| **拍板** | 你 | 需求变更、验收、发布 |

---

## 1. 流程（五步，不许跳）

```
① 任务卡   实现方按 WORKPLAN 出：目标 / 接口 / 不变量 / 验收条件 / 禁改范围（波及外部契约时契约守门确认）
② 实现     实现方写代码 + 测试，本地跑通
③ 自检     交付前必须贴出：测试输出 + selfcheck 结果
④ 评审     契约守门逐条对「评审清单」（§4）
⑤ 合入     你点头才合；提交信息只写内容，无签名行
```

**一次只交一个模块。** diff 控制在 ~600 行以内（含测试）。超了说明任务卡切得不对，退回重切。

## 2. 任务卡模板

```md
### 任务：lib/<name>.mjs
- 目标：一句话
- 接口：（签名 + 输入输出类型）
- 不变量：（可被断言的事实，≥3 条）
- 依赖：只能 import 本包其它 lib/* 与 ../protocol
- 禁改：docs/、其它 lib 文件、package.json 依赖
- 验收：`node --test test/<name>.test.mjs` 全绿 + 每条不变量都有断言
- 依据：docs/ARCHITECTURE.md §X / docs/DECISIONS.md D-YY
```

## 3. 硬规则（红线，违反即退回）

### 3.1 代码边界

| 规则 | 原因 |
|---|---|
| `lib/` 内**禁止** import cordis / `@deepseek-ai/*` | 只有 `index.js` 碰宿主；lib 必须是纯逻辑，才能脱离 DSH 单测 |
| 业务逻辑不得出现在 `index.js` | `index.js` 只做装配：注册工具、起时钟、接事件 |
| 所有写库必须经 `store.mjs` 的 `withWriteLock` | `node:sqlite` 是同步 API，并行写会同步阻塞到超时（实测 803ms 报 `database is locked`） |
| 所有外发必须经 `audit.mjs` | 绕过审计的发声 = 事故 |
| 时间与随机数必须注入 | `clock` 与 `rng` 作为参数传入，测试要能穿越时间、复现随机 |
| 新增依赖须先批准 | 除 `dsh-living-protocol` 外，默认零依赖 |

### 3.2 宿主的六个坑（全部来自 `dsh-bili-scroll` 实战）

1. Config 每个字段必须 `.extra('volatile', true)`，否则 `settings.update()` 抛错
2. loader entry 的 `id` 必须等于命名空间名，且模块必须导出 `Config`
3. 别裸 import 可选 peer 依赖——桌面版 `autoInstallPeers: false`，拿不到会让**整条插件不激活**
4. schema 里别写会校验失败的约束（如 `.max(20)`）——校验不过 ⇒ 整个 entry 被拒
5. tick 回调必须 try/catch——`setInterval` 里抛错会带走宿主进程
6. 所有后台 timer 必须 `.unref()`

### 3.3 风格

- 注释只写**为什么**，一行，不写"这行做了什么"
- 不写自描述代码的注释；复杂逻辑先改结构，写不清就说明结构错了
- 测试用 `node --test`，不引测试框架

## 4. 评审清单（逐条对）

- [ ] 每条不变量都有对应断言，且断言能失败（改坏实现时测试要红）
- [ ] 没有 `Date.now()` / `Math.random()` 直接调用
- [ ] 没有绕过 `withWriteLock` 的写库
- [ ] 没有绕过 `audit` 的外发
- [ ] `lib/` 没有 import 宿主包
- [ ] 失败路径有类型化错误码（见 protocol 的码表），不是裸 `throw new Error('...')`
- [ ] 违背了哪条决策？——若确实要违背，先改 DECISIONS 再改代码

## 5. 契约变更流程

**代码不能悄悄改契约。**

```
发现契约有问题 → 提案（哪条决策/D-YY、为什么、影响面）
             → 拍板
             → 先改 docs/DECISIONS.md（新增或改写一条）
             → 再改实现
```

反之：实现过程中"顺手"发现更优雅的写法，只能记进 `docs/TODO.md`，不许当场改契约。

## 6. 交付时贴什么

```
1. 改了哪些文件（逐文件说明）
2. node --test 输出（全绿，贴原始输出）
3. 不变量 ↔ 断言 对照（哪条断言守哪条不变量）
4. 已知未做 / 风险（诚实写，不写"无"除非真的没有）
```

## 7. 我（契约守门）交付什么

| 交付物 | 时机 |
|---|---|
| `packages/protocol/` 的类型与 schema | 实现开工前 |
| 任务节点与里程碑的确认（`docs/WORKPLAN.md`） | 每期开工前 |
| 每个模块的任务卡确认 | 逐模块 |
| 宿主内探针（S1 / S2） | 接口冻结后、实现前 |
| 评审结论 | 每次 PR |

## 8. 明确不做的事

- 不做代码生成式评审（"看起来不错"不算评审）
- 不为通过测试而改测试的期望值
- 不在同一 PR 里既改契约又改实现
